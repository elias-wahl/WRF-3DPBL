\section*{The five core bullets}

\paragraph{1 --- Objective.} 20\,m WRF-LES of the Radfeld transect (Inn Valley,
TEAMx) to derive correction functions for UAS-measured turbulence --- the
objective of the DFG-funded partner project (virtual flights along the real
ascent trajectories, identical processing chain). Complementary objective of
the FWF-funded applicant: the same runs as turbulence reference for evaluating
a 3D PBL closure in the 500\,m grey zone.

\paragraph{2 --- Funding context.} The UAS data, processing chain and joint
analysis are contributed by the DFG-funded group at Tübingen (Platis); the
applicant's own position is FWF-funded. Results feed the DFG project's work
packages directly; research stay in Tübingen spring 2027.

\paragraph{3 --- Feasibility.} Production only: a validated ICON-driven 500\,m
WRF setup of the valley is in continuous research use with measured
throughput; a 100\,m LES of the same valley exists in the group (Freddi 2026)
and supplies the intermediate nest; no methodological development on Levante.

\paragraph{4 --- Scope and request.} Six cases from the two TEAMx intensive
periods. The parent chain (500\,m\,$\to$\,100\,m) runs full diurnal cycles;
the 20\,m nest --- 97\,\% of the cost --- runs \emph{only the windows the
measurements need}: three cases through the evening and night (14\,h each),
three daytime-only (10\,h each), plus a three-member sensitivity suite on a
6\,h window. \textbf{Request: 22\,000 node-hours, 15\,TB work / 5\,TB
archive}, post-processing included.

\paragraph{5 --- Data value.} One reference dataset serving three uses --- UAS
correction functions (DFG partner project), grey-zone evaluation of a 3D PBL
closure (FWF-funded applicant project), and the first LES-resolved nocturnal
cold-pool budget of this valley --- documented and shared with the TEAMx
community.

\section*{Verwendete Software}
\begin{itemize}
\item \textbf{Model:} WRF (ARW) 4.8.0, institutional fork carrying a
  three-dimensional Mellor--Yamada boundary-layer closure developed in this
  project; Fortran 90, \textbf{pure MPI} (\texttt{dmpar}, configure option 34,
  Linux x86\_64 / gfortran), no OpenMP, basic nesting.
\item \textbf{Compiler and MPI (production build):} GCC \textbf{12.2.0} with
  \textbf{OpenMPI 4.1.6}, Spack-provided and version-pinned. The same
  combination (GCC 11/12 + OpenMPI 4.1) exists in Levante's module stack, so no
  porting work is requested. \ver{} exact Levante module strings.
\item \textbf{I/O and numerics libraries:} netCDF-C 4.9.0, netCDF-Fortran
  4.6.0, HDF5, zlib 1.2.13, \textbf{netlib-LAPACK 3.10.1} --- the closure
  solves a dense $10\times10$ second-moment system per grid point and time step
  with LAPACK \texttt{dgesvx} (equilibrated, condition-estimated), so a tuned
  LAPACK/BLAS matters for throughput.
\item \textbf{LES configuration:} Deardorff 1.5-order TKE closure in the nested
  LES domains; RK3 split-explicit dynamics on the terrain-following grid;
  Thompson microphysics, RRTMG radiation, Noah-MP land surface, topographic
  shading active.
\item \textbf{Pre-processing:} WPS (ungrib/metgrid) plus an in-house ICON
  converter (Python + ecCodes) that reads the ICON-500\,m forecasts on their 65
  native model levels and writes WPS-ready GRIB2 --- the step that removed a
  documented initialization deficiency of the pressure-level product.
\item \textbf{Post-processing:} Python 3 (netCDF4, NumPy, SciPy, xarray/dask,
  matplotlib) in a pinned Conda environment, plus WRFlux for online flux and
  budget decomposition. All pre- and post-processing runs through SLURM, hence
  its own compute request.
\item \textbf{Workflow:} restart-segmented chains with SLURM dependencies and
  automatic per-segment quality gates; no interactive steps in production.
\end{itemize}

\section*{Suitability to HLRE-4 (Levante)}
\begin{itemize}
\item \textbf{The problem needs a machine of this class.} A two-stage nested
  large-eddy simulation, 500\,m\,$\to$\,100\,m\,$\to$\,\textbf{20\,m}, over the
  instrumented Radfeld transect: $\approx$131$\times$10$^6$ grid points in the
  innermost domain at $\Delta t \approx 0.1$\,s, run as one restart-continuous
  chain rather than independent short jobs --- beyond local resources within the
  project's lifetime.
\item \textbf{The code matches the architecture.} Pure-MPI Fortran with a
  regular Cartesian decomposition maps directly onto Levante's CPU partition
  (AMD EPYC Milan, 128 cores per node \ver); throughput is \emph{measured} on
  the same processor generation, so the request rests on measurement rather than
  estimate. Communication is nearest-neighbour halo exchange plus the per-step
  pressure solve --- well served by the HDR InfiniBand fabric.
\item \textbf{Resource type requested: CPU only.} The model has no GPU port, so
  the A100 partition is explicitly not requested; remote visualization is not
  required.
\item \textbf{Memory and I/O fit.} The standard 256\,GB nodes suffice at the
  planned decomposition, with fat-memory nodes as a fallback \ver; output is
  thinned at source through field-selection lists, one file per output time, and
  the aggregate write rate is well inside what Levante's Lustre \texttt{/work}
  sustains.
\item \textbf{The scientific environment is at DKRZ.} The driving data are ICON
  forecasts --- a DKRZ-native model whose holdings and tooling live on the same
  system --- and the analysis chain (virtual UAS flights, spectra, statistics)
  runs in the same SLURM environment as the simulations.
\item \textbf{Why HLRE-4 rather than the applicants' national systems:} the
  principal investigator, the UAS observations and the processing software are
  with the DFG-funded partner group in Germany, and the LES production volume
  exceeds what the Austrian allocation can absorb alongside the 500\,m ensemble
  it already carries.
\end{itemize}

\section*{Scalability}

Measured strong scaling of the production configuration, 500\,m domain
($601\times501\times80 = 24.1\times10^6$ points, $\Delta t = 2$\,s), 128 MPI
ranks per node:

\begin{center}
\begin{tabular}{@{}rrrr@{}}
\toprule
nodes & ranks & s per time step & node-hours per 6\,h segment \\
\midrule
2 & 256 & 1.50 & 9.0 \\
4 & 512 & 0.80 & 9.6 \\
5 & 640 & 0.65 & 9.8 \\
\bottomrule
\end{tabular}
\end{center}

\begin{itemize}
\item Near-linear to 640 ranks: a 2.3$\times$ speed-up for 2.5$\times$ the
  nodes ($\approx$92\,\% parallel efficiency) at $\approx$38\,000 grid points
  per rank.
\item \textbf{Extrapolation to the LES nest:} holding that points-per-rank
  figure, the $131\times10^6$-point domain implies $\approx$3\,500 ranks ---
  \textbf{20--32 nodes per LES segment}, the size planned for production. The
  halo-to-compute ratio there is no worse than in the measured cases because the
  subdomain column count is comparable.
\item \textbf{A short on-machine scaling test (16/32/64 nodes, one simulated
  hour) is planned in the first weeks} to confirm the extrapolation on Levante's
  fabric and fix the production node count; its cost is included below.
\item \textbf{Time-step constraint, stated openly:} the LES nest is limited by
  the vertical Courant number in thin near-surface layers over steep terrain ---
  a limit this project has measured directly and mitigates with WRF's targeted
  vertical-velocity damping rather than a globally shorter time step, which is
  what keeps the cost estimate stable.
\item \textbf{I/O scaling:} one file per output time and domain; field selection
  at source reduces a full 3-D frame by roughly a factor three. Output cadence is
  a tunable, not a fixed cost.
\end{itemize}

\paragraph{Justification of each choice.}
\begin{itemize}
\item \textbf{Six cases:} two TEAMx intensive observation periods, three cases
  each, to span the flow regimes the UAS flights sampled; fewer would not
  separate case-to-case scatter from the correction functions being derived.
\item \textbf{Only three cases carry the night:} the nocturnal window doubles
  the LES hours per case and serves the secondary objective (the cold-pool
  budget), not the UAS correction functions, which are flown by day. Three
  nights suffice to show whether the nocturnal result is robust; the other three
  cases stop at the evening transition.
\item \textbf{The nest runs windows, not whole days:} the virtual-flight
  comparison needs the LES only where flights exist, plus $\approx$2\,h of LES
  spin-up. Running the nest for 26\,h per case would roughly triple the cost and
  add no measurement.
\item \textbf{A 30\,\% margin:} the chain is restart-segmented and has been in
  production for months, so failure recovery is cheap; 30\,\% covers first-weeks
  setup on a new machine and lost segments.
\item \textbf{The post-processing line item:} all analysis runs through SLURM at
  DKRZ; resampling $\approx$40 flight trajectories through several TB of LES
  frames and computing spectra over the nest volume is not a login-node task.
\end{itemize}

\section*{DKRZ process constraints (allocation rules, retrieved 2026-09-08)}
\begin{itemize}
\item \textbf{Eligibility / PI:} the PI should be at a German research
  institution $\Rightarrow$ the proposal is \textbf{led by Tübingen (Platis)};
  Innsbruck joins as international partner supplying and running the model
  system.
\item \textbf{Windows:} Sep 1 -- Oct 31 (start Jan 1) and Mar 1 -- Apr 30 (start
  Jul 1); allocations run 12 months. \textbf{Current window open, deadline
  2026-10-31, start 2027-01-01.}
\item \textbf{Compute expires quarterly} --- consumption must be roughly even. A
  Jan 1 start would force $\approx$5\,500 node-h per quarter from January; LES
  production is planned H2 2027, so either front-load the sensitivity suite and
  the scaling test into Q1/Q2 or target the spring window (start 2027-07-01).
  \emph{Decide before writing.}
\item \textbf{Document limits:} first proposal $\le$8 pages, $\le$4\,000
  characters per page; required sections include scalability (covered above).
  Renewals: $\le$2-page report.
\item \textbf{Storage policy:} disk is per allocation period (re-request on
  renewal; move data to archive within the period); unused archive grants expire.
\end{itemize}

\section*{Proportionality (internal, not for the Antrag)}
\begin{itemize}
\item Levante's CPU partition is $\approx$2\,800 nodes \ver, i.e.
  $\approx$24.5$\times10^6$ node-hours per year. The request is
  \textbf{$\approx$0.09\,\% of a machine-year} and 2.2\,\% of the volume at
  which DKRZ demands a data-storage plan.
\item For a DFG project funding one doctoral position, whose computational core
  this is, $\approx$22\,000 node-hours over twelve months is proportionate: one
  PhD-year of production, not a community campaign. The earlier 50\,000-hour
  version was defensible but harder to argue and, under quarterly expiry, less
  likely to be fully consumed --- which matters for the renewal.
\item \textbf{If reviewers ask for less:} two sensitivity members and two night
  cases give $\approx$18\,000 node-hours without touching the primary objective.
  Natural mid-period extensions if more becomes possible: the three additional
  nights and a 10\,m stable-night pilot.
\end{itemize}
